# Session 25 — 2026-10-24 : ZYWRLE complet, issue #22

## Cause du « gap » de la session 11
La session 11 (2026-09-09, QEMU 8.2.2) avait vu des subencodings 17-126,
réservés par la RFC, dès la deuxième tuile d'un rectangle ZYWRLE. Ce n'est
pas un format de tuile. La lecture du code source tranche :

- **QEMU** `ui/vnc-enc-zrle.c.inc`, branche Raw de `ZRLE_ENCODE_TILE` : il
  écrit l'octet `0`, puis, si `zywrle_level > 0` et que le bit `0x80` n'est
  pas posé, applique `ZYWRLE_ANALYZE` à la tuile et **se rappelle lui-même**
  avec `zywrle_level | 0x80`. La tuile ZYWRLE est donc un octet `0` suivi
  d'une tuile ZRLE imbriquée complète (unie, palette, RLE ou Raw) dont les
  pixels sont les coefficients d'ondelettes.
- **libvncclient** `zrle.c` (`HandleZRLETile`) fait l'inverse : sur un type 0
  avec `zywrle_level > 0`, il décode la tuile imbriquée en place puis appelle
  `ZYWRLE_SYNTHESIZE`.
- Le niveau n'est jamais transmis. QEMU (`vnc-enc-zrle.c`) : 0 si `lossy`
  est désactivé, sans qualité annoncée ou à la qualité 9 (il envoie alors du
  ZRLE, 16) ; sinon 3 (qualité 0-2), 2 (3-5) ou 1 (6-8). libvncclient :
  `3 - qualité / 3`, même table.

Le fork lisait la tuile imbriquée comme `w*h*3` octets Raw, puis prenait un
octet de données pour le subencoding suivant : d'où le 28 observé.

## Implémentation
- `_zywrle_harr()` et `_zywrle_synthesize()` (numpy) : port de `Harr`,
  `InvWavelet`, `ZYWRLE_UNPACK_COEFF`, `ZYWRLE_YUVRGB` et des macros
  `*_UNALIGN` de `common/zywrletemplate.c` (libvncserver). Les octets 0-2 du
  CPIXEL sont traités comme les octets 0-2 d'un pixel 32 bits petit-boutiste,
  ce que négocie `Video.create()`.
- `Video._xrle_tile()` décode une tuile (extrait de `process_xrle()`), avec
  l'appel imbriqué ; `Video.jpeg_quality` conserve la qualité annoncée pour
  calculer le niveau dans `Video.read()`.
- Les subencodings 17-126 restent refusés (`ValueError`), y compris dans une
  tuile imbriquée.

## Vérifications
- **Contre le C de référence** : `common/zywrletemplate.c` de libvncserver
  compilé (`BPP 32`, petit-boutiste, `ZYWRLE_ENCODE` + `ZYWRLE_DECODE`).
  400 cas aléatoires (1x1 à 64x64, niveaux 1-3, tailles non alignées), dont
  205 allers-retours `ZYWRLE_ANALYZE` → synthèse : sortie Python identique
  octet par octet. Dix de ces cas sont figés dans `ZywrleTests.VECTEURS_C`
  (entrées reproductibles, empreinte SHA-256 de la sortie C).
- **Contre un vrai QEMU 10.2.1** (`-vnc :N,lossy=on`), secteur d'amorçage
  de 47 octets (mode 13h). La vérité terrain est le `screendump` du moniteur.
  - Dégradé par blocs : ZYWRLE aux niveaux 1, 2 et 3 identique au pixel près
    (coefficients haute fréquence nuls) ; 210 tuiles sur 3 captures, toutes
    passées par la synthèse.
  - Motif `(x*y + (x^y)) >> 1` (riche en hautes fréquences) :

    | Encodages | Qualité | Niveau | Erreur moyenne | PSNR |
    |---|---|---|---|---|
    | ZRLE | — | — | 0 | sans perte |
    | ZYWRLE, ZRLE | 0 | 3 | 15,71 | 21,1 dB |
    | ZYWRLE, ZRLE | 4 | 2 | 8,66 | 26,0 dB |
    | ZYWRLE, ZRLE | 7 | 1 | 0,17 | 55,9 dB |
    | ZYWRLE, ZRLE | 9 | 0 (ZRLE) | 0 | sans perte |

  La qualité monte avec le réglage, comme attendu d'un encodage à perte ;
  avant le correctif, chaque capture ZYWRLE levait `ValueError`.
  `test_live_qemu_zywrle.py` rejoue ces cas dans le job CI « Serveur réel ».

## Décision
`Enc.ZYWRLE` reste hors de `Enc.default()` : le décodage est complet, mais
l'encodage est à perte. Un appelant qui ne donne `jpeg_quality` que pour
Tight ne doit pas récupérer d'artefacts d'ondelettes dans les rectangles
ZRLE sans l'avoir demandé.
