# Session 27 — 2026-11-10 : variantes RSA-AES RA2ne/RA2r, issue #26

## Objectif
L'issue #26 demandait d'implémenter les variantes RSA-AES
RA2ne/RA2ne_256/RA2r/RA2r_256 (types de sécurité 6/130/13/133), jusqu'ici
délibérément écartées.

## Sources croisées
- `rfbproto.rst` (récupéré via l'API GitHub du dépôt `rfbproto/rfbproto`) :
  sections « RSA-AES Security Type », « RSA-AES-256 Security Type » et
  « RSA-AES Two-step Security Type » (lignes ~1099-1320). RA2ne : « only
  the handshake is encrypted, SecurityResult and everything after stays
  in the clear ». RA2r : « a second round of key derivation after the
  credentials, this time over AES-EAX instead of RSA », avec échange de
  deux nouveaux aléas et dérivation de nouvelles clés de session.
- TigerVNC `common/rfb/CSecurityRSAAES.cxx` + `SSecurityRSAAES.cxx`
  (récupérés via `gh api -H "Accept: application/vnd.github.raw"`) :
  couvre RA2/RA2ne uniquement — **aucune des deux classes n'implémente
  RA2r**, et le code serveur ne propose même pas RA2ne dans les types
  annoncés par défaut. Aucune implémentation de référence ouverte de
  RA2r n'existe donc (RealVNC est propriétaire).

## Choix de lecture (RA2r)
La prose de la spec ne dit pas explicitement qui envoie son nouvel aléa
le premier. Hypothèse suivie et documentée dans la docstring : le client
écrit le sien puis lit celui du serveur, par symétrie avec la ronde 1 où
le client de TigerVNC écrit avant de lire. Les nouveaux aléas transitent
chiffrés en AES-EAX (clés de la ronde 1), pas par RSA ; la formule de
dérivation est la même qu'à la ronde 1 (SHA-1/SHA-256 de la
concaténation des deux aléas, tronquée à la taille de clé) ; les objets
`_EAXReader`/`_EAXWriter` neufs repartent avec l'index de message à zéro,
comme l'exige la spec. Rien n'indique un échange de hachage des clés
publiques dans cette ronde : la spec n'en parle pas, on n'en envoie pas.

## Implémentation
- `_rsa_aes_negotiate()` : deux mots-clés uniquement (`chiffre_session`,
  `seconde_derivation`), valeurs par défaut inchangées (RA2/RA2_256
  existants non touchés). RA2ne rend le lecteur/écrivain bruts ; RA2r
  refabrique une paire `_EAXReader`/`_EAXWriter` sous les nouvelles clés.
- `Client.create()` : la boucle de préférence devient
  `(33, 1, 2, 19, 129, 5, 133, 13, 130, 6, 113, 20)` — 256 avant 128,
  chiffré de bout en bout (RA2 puis RA2r) avant RA2ne, qui ne chiffre que
  la poignée de main ; l'appel de négociation traduit le type choisi en
  `key_bits`/`chiffre_session`/`seconde_derivation`.
- Un bug trouvé par le test unitaire lui-même : la première version de la
  dérivation de la ronde 2 inversait l'ordre des aléas dans les hachages
  (clé lecteur/écrivain permutées) — jeton EAX invalide immédiat sur la
  lecture du SecurityResult. Corrigé en reproduisant exactement la
  convention de nommage de la ronde 1 (`client_session_key` chiffre ce
  que le client envoie, `server_session_key` ce qu'il lit).

## Limites
Aucune vérification contre un vrai serveur : TigerVNC n'implémente ni
RA2r ni (côté client) RA2ne en pratique de test, et aucun serveur
installable dans ce sandbox ne propose ces variantes. Le round-trip
prouve la cohérence interne avec la spec, pas l'interopérabilité. La
ligne du backlog et la docstring documentent ce statut et l'hypothèse
d'ordre d'envoi pour RA2r.
